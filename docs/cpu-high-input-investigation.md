# 高速输入 CPU 偏高排查（准备）

状态：P0–P6 结构优化已完成；用户反馈高速输入下 CPU 最高约 12–13%，内存正常。  
目标：先确认是否为真实回归，再定位到具体改动；不先改架构。

## 1. 已知基线

- 历史高速输入普通模式：约 **12%**（P2.6 阶段记录）。
- 历史空闲/普通：CPU/GPU < 8%，60fps。
- 16K 设置关闭：私有 113–117MB，工作集 236–239MB。
- 当前 P6 空闲对比（P1.2 → P6）：CPU 4.88% → 2.93%，工作集 238.3 → 239.0MB。

结论：12–13% 与历史 12% 很接近，必须先做同场景 A/B，避免把测量噪声当回归。

## 2. 主要嫌疑

| 优先级 | 改动 | 机制 |
|---|---|---|
| 高 | P4.3 `IRenderBackend` | KeyRenderer/TextLayout 从具体类改为接口，所有绘制原语走接口 dispatch |
| 中 | P4.7 `KeySlot` | `DrawKeys` 的 tuple 解构改为 `Deconstruct` 方法调用 |
| 低 | P4.1/P4.2 `CountFormatter`/`TextLayout` | 每段文本多一次静态方法/文化信息调用 |
| 排除 | P2/P3/P5 | 启动、设置、配置迁移不在每帧/输入热路径 |

## 3. 对照版本

- `checkpoints/2026-11-08_0533-P1.2-ZeroWarnings/`：P2 结构拆分前。
- `checkpoints/2026-11-08_0752-P4-Complete/`：含接口/KeySlot。
- `checkpoints/2026-11-08_0808-P6-Audit/`：当前版本。
- `checkpoints/2026-11-08_0833-Current-Before-CPU-Investigation/`：本次排查前快照。

## 4. 测试方法

1. 同一份 16K 配置，普通模式，GPU 默认；
2. 关闭 OBS/浏览器等后台；
3. 启动临时副本，聚焦显示窗口；
4. 用 `tools/bench-high-input.ps1` 以 30 次/秒发送已注册键，持续 15 秒；
5. 记录 CPU 时间占比、工作集、私有内存；
6. 每个版本重复 3 次，取中位数。

## 5. A/B 修复顺序

如果确认 P6 高于 P1.2：

1. 保留 `IRenderBackend` 定义，但把 `KeyRenderer`/`TextLayout` 热路径参数改回 `TransparentRenderer`，测一次；
2. 若仍高，把 `DrawKeys` 的 `Deconstruct` 改回直接字段访问，测一次；
3. 若仍高，再对比 `CountFormatter` 的 `CultureInfo` 路径。

每次只改一个变量，禁止同时改多处。


## 6. 程序内置采样（当前版本）

新版本每 5 秒写 [PERF] 到 JipperKeyViewer-debug.log：

`
[PERF] up=..s cpu=..% cpu_ms=.. ws=..MB private=..MB managed=..MB handles=.. threads=.. fps=.. kps=.. total=..
`

- cpu 按逻辑核心归一化，接近任务管理器口径；
- 首条样本含启动/JIT，至少看连续 3 条；
- 高速输入时重点对比 cpu、ps、kps；
- 如果 kps 很低但 CPU 高，问题不在按键计数路径。


## 7. 实测结果（2026-11-08）

用户日志（16K，GPU，普通模式）：

| 场景 | KPS | CPU | 工作集 | 私有 |
|---|---:|---:|---:|---:|
| 空载 | 0 | 4.1–4.4% | 241–242MB | 119–120MB |
| 输入上升 | 40 | 8.4% | 255MB | 133MB |
| 高频 | 73–139 | 11.6–14.6% | 250–258MB | 127–135MB |

程序内 A/B（30 次/秒，15s）：

| 版本 | CPU | 工作集 | 私有 |
|---|---:|---:|---:|
| P1.2 | 3.12% | 245.8MB | 123.1MB |
| P4 | 3.12% | 249.7MB | 127.4MB |
| P6 | 3.59% | 249.4MB | 127.1MB |

120 次/秒，15s（单次）：

| 版本 | CPU |
|---|---:|
| P1.2 | 7.68% |
| P4 | 7.45% |
| P6 | 8.98% |

结论（暂定）：

1. CPU 随 KPS 明显上升，12–14.6% 与历史高速输入“约 12%”同档；
2. P4（接口/KeySlot）没有比 P1.2 更高，P6 的 +1.3% 更像单次噪声；
3. 暂无证据表明 P2/P3/P5 结构拆分导致回归；
4. 高频输入下的文本 sprite/KPS 更新是主要 CPU 来源。
5. 需要重复 3 次、取中位数后再决定是否做接口/KeySlot 回退 A/B。
